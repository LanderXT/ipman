# ipman v2.4 — UTF-8 slugs, --import-plan, doc gap-fill

ipman v2.4 is **purely additive over v2.3**. The JSON protocol stays at `protocol_version: 2`; no operations were renamed or removed; every v2.0–v2.3 client keeps working unchanged. v2.4 sharpens four sharp edges that surfaced in real use:

1. UTF-8 titles produced empty or garbled slugs.
2. The `--usage` text was approaching a latent C99 string-literal limit.
3. Several already-shipped features were under-documented in `SKILL.md`.
4. There was no atomic way to re-import a `plan.export` snapshot into a fresh workspace.

A fifth phase (sub-tasks UX) was scoped, designed, and **deferred** to v2.5+ on the finding that `parent_task_id` was already in the schema.

---

## What's new at a glance

| Group | Change | Replaces |
|---|---|---|
| Slug generation | `ipman_slugify` decodes UTF-8 codepoints and transliterates Latin-1 Supplement + Latin Extended-A via a 192-entry table (`á → a`, `ñ → n`, …) | ASCII-only slug emitting empty strings or `?` for non-ASCII titles |
| `--usage` | Embeds `src/usage_text.txt` as a byte array via `scripts/embed_usage.sh` (mirrors `embed_skill.sh`) | A single 4 KB string literal that was approaching the C99 4 095-char limit |
| Documentation | `SKILL.md` adds `phase.move`, cross-plan `task.list` (no `plan_id`), multi-scope `instruction.list`, and an expanded `--dry-run` callout. README counts refreshed (76 ops / 13 entities). | Hidden features that operators rediscovered through reading source |
| CLI | `ipman --import-plan <file.json>` consumes a `plan.export` envelope, allocates fresh ids, saga-rolls-back on failure | Hand-orchestrating `plan.create` + `phase.create` + `task.create` from a snapshot |
| Schema version | No DB migration | — |

Surface stays at **76 ops / 13 entities** (no new ops; `--import-plan` is a CLI-side orchestrator, not a JSON op).

## Why each change exists

### Slug i18n

Slugs are derived from titles to populate the unique `label` columns on `plan`, `phase`, and `task`. Pre-v2.4 the slugifier dropped any byte ≥ 0x80, producing `""` or `"?"` for titles like `"Próxima fase"` or `"Configuración"`. That collided with other rows or failed the non-empty check.

v2.4 keeps the ASCII fast path **byte-identical** (verified by `tests/unit/test_slugify.c`) and adds a single `decode_utf8` step plus a 192-entry transliteration table when a non-ASCII byte appears. The table covers Latin-1 Supplement (0x80–0xFF) and Latin Extended-A (0x100–0x17F) — sufficient for Spanish, Portuguese, French, German, Italian, and most Eastern European Latin orthographies. CJK and Cyrillic still fall through to a single underscore; v2.5+ may extend the table.

```text
"Próxima fase"    → "proxima-fase"
"Configuración"   → "configuracion"
"phase 1: déjà"   → "phase-1-deja"
"日本語"          → "_"     (CJK fallthrough)
```

Tests: `tests/unit/test_slugify.c` (16 cases), `tests/integration/230_slugify_diacritics.sh`.

### --usage byte-array embed

Pre-v2.4 the `print_usage` function held the entire help text as one string literal in `src/main.c`. C99 §5.2.4.1 only requires implementations to support string literals up to 4 095 bytes; a few more lines would have hit the limit. v2.4 moves the text to `src/usage_text.txt` and embeds it at build time as a `static const unsigned char` array via `scripts/embed_usage.sh`, mirroring how `SKILL.md` is already embedded. Output is byte-identical (4 883 bytes); the latent limit is gone.

### Doc gap-fill

A "second-opinion" review of v2.3 surfaced features that worked but were not findable from `SKILL.md`:

- `phase.move` (reorders phases within a plan) was reachable via the JSON API but missing from the agent skill.
- `task.list` accepts no `plan_id` to query across plans; the doc implied it was plan-scoped.
- `instruction.list` accepts `entity_type` ∈ `{plan, phase, task, project}`; the multi-scope use was undocumented.
- `--dry-run` was a one-line aside; it deserved a dedicated callout.

v2.4 phase 25 surfaces these in `SKILL.md` and `agent_docs.c` "Common Verbs". The fix is documentation only.

### --import-plan

`plan.export` returns a canonical JSON snapshot of a plan and its dependents. Before v2.4 the only way to re-import that snapshot was to hand-orchestrate `plan.create` + `phase.create` + `task.create` + `task.link_dependency` calls in the right order, which was tedious and not atomic.

`ipman --import-plan <file.json>` does the orchestration as a **client-side** verb (NOT a JSON op — that decision is captured in `pman` plan IPMAN-V2-4 task 26 comment 14). Implementation lives in `src/import_ops.c` (~911 lines). Key properties:

- Allocates **fresh ids** for every entity — the snapshot's ids are reference-only.
- **Saga rollback**: on any failure mid-import, the partially-imported plan is `task.cancel`-ed, `phase.close(canceled)`-ed, and `plan.close(canceled)`-ed so the workspace is left in a known-terminal state. `tests/integration/250_plan_import_rollback.sh` grep-asserts the cleanup path actually ran.
- **Skips events, closures, and project-scoped instructions** deliberately. Events are append-only audit; recreating them with new ids would lie. Closures attach to entities whose ids changed. Project-scoped instructions live above the plan.

Tests: `tests/integration/240_plan_import_happy.sh`, `tests/integration/250_plan_import_rollback.sh`.

### Sub-tasks: design, then defer

The original v2.4 plan included a "sub-tasks" phase to add UX for hierarchical task structure. During design it surfaced that the schema already has `parent_task_id` (from v2.0), and `task.create` already accepts it. What was missing was only **surface**: a filter on `task.list`, a render in `--next`, a creation shortcut. The decision: ship those in v2.5 once we have a clearer signal of demand. v2.4 phase 27 closed the design exercise. Decision artifact: [`docs/superpowers/specs/2026-05-04-subtasks-deferred.md`](superpowers/specs/2026-05-04-subtasks-deferred.md).

## Migration

Nothing to do. v2.4 is wire-additive: the JSON protocol is unchanged, no operations were renamed or removed, no DB migration ships, and the binary's `--usage` output is byte-identical. Existing scripts, agents, and clients keep working with no edits.

Slugs generated by **older binaries** for non-ASCII titles will still be whatever they were (often empty or `?`). v2.4 does not retro-fix existing rows; it only changes generation going forward. If you have rows with empty `label` columns from before v2.4, regenerate them by `task.update` (or `phase.update` / `plan.update`) — the slugifier will emit a Latin-aware label this time.
