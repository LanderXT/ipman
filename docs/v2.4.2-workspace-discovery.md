# ipman v2.4.2 — workspace discovery and silent-fork prevention

ipman v2.4.2 is a **point release** to v2.4.1 that closes a class of agent failures where ipman, run from a subdir or git worktree without `IPMAN_HOME` set, would silently initialize a stray workspace alongside cwd — divorced from the data the user actually cared about. The JSON protocol stays at `protocol_version: 2`; no operations were added, renamed, or removed; existing well-positioned clients are unaffected.

---

## The hazard

Before v2.4.2, the workspace path resolved with two-line precedence:

1. `$IPMAN_HOME` if set and non-empty.
2. Otherwise: `./.ipman` literally — relative to the current working directory.

That `./.ipman` is the trap. Three agent scenarios broke quietly:

- **Agent runs from a subdir.** A subagent dispatched to `/proyecto/src/` to do focused work executes `ipman --next`. cwd has no `.ipman/`, so the read fails with "not initialized". If the agent's recovery heuristic is to run `ipman init` (a reasonable inference from the error message), the result is a stray `.ipman/` planted in `src/` — separate from the workspace at `/proyecto/.ipman/`.

- **Agent runs from a git worktree.** Worktrees share the parent repo's `.git/` (via a `.git` *file* in the worktree, not a directory) but have their own working tree on disk. The parent's `.ipman/` is **gitignored** and does not propagate. The agent enters the worktree, sees no `.ipman/`, runs `init`, and the worktree's plan history starts diverging from the canonical workspace.

- **Agent runs from `/tmp` or `$HOME` after a failed cd.** Same shape: cwd has no `.ipman/`, `init` succeeds, the workspace is now an orphan.

The bug is asymmetric: reads fail loudly ("not initialized"); writes (specifically `init`) succeed silently. The silent success is what burns operators — the agent reports progress but the progress lives in a workspace that will be deleted with the worktree, ignored when the user looks for it, or bury the legitimate one in confusion.

This was reported by an operator who observed exactly this scenario when the Superpowers plugin dispatched a subagent into a worktree.

---

## What's new at a glance

| Change | Detail |
|---|---|
| Resolution precedence | `IPMAN_HOME` (escape hatch, total bypass) → `<repo-root>/.ipman` (walks cwd upward looking for `.git` file or directory) → `./.ipman` legacy fallback (when no `.git` ancestor exists). |
| Subdir/worktree support | A read or write op from `/proyecto/src/` now resolves to `/proyecto/.ipman/`, not `src/.ipman/`. No agent intervention needed. |
| `init` refuse | If cwd is inside a git repo but is **not** the repo root, `init` refuses with `validation_failed` and a clear message naming the relative path to the root (e.g. `init must run at the repo root (".." relative to cwd)…`). |
| New helper | `ipman_home_repo_root_relpath` returns the cwd-relative path of the resolved repo root (or `-1` when discovery does not apply). Used by `init`. |
| Exit-code semantics | `validation_failed` from `init` now correctly exits 0 (semantic, recoverable), matching the JSON dispatch path. Previously CLI-direct verbs always exited 1 regardless of error category. New helper `emit_op_error` honors `ipman_error_is_fatal`. |

Surface stays at **76 ops / 13 entities**. No DB migration. No protocol bump.

## Resolution precedence, illustrated

```
$IPMAN_HOME set non-empty?
├── yes → use it, no validation, no walk    (operator escape hatch)
└── no
    └── walk cwd upward, lstat each `<dir>/.git`
        ├── found (file or dir) → resolve to <dir>/.ipman, expressed
        │                          relative to cwd ("../.ipman", etc)
        └── not found (cwd is not under any repo) → use "./.ipman"
                                                    (legacy default)
```

The middle branch is the new one. It captures both normal clones (where `.git` is a directory) and worktrees (where `.git` is a file pointing into the parent's `.git/worktrees/`). A single `lstat` per ancestor handles both.

## What `init` refuses

`init` is the only op that fundamentally creates state, so it is the only op where the silent-fork hazard has teeth. v2.4.2 adds one check at the top of `run_init`:

```text
if cwd is inside a git repo AND cwd is NOT the repo root:
    refuse with validation_failed, exit 0,
    error.message names the relative path to the root.
```

Other ops do not refuse — they discover and use the repo-root `.ipman/`. That asymmetry is deliberate:
- Reads/writes against an existing workspace are not destructive; finding the right `.ipman/` automatically is strictly better than failing.
- `init` is the one place where "I will create a new workspace at cwd" is the user's literal request. Refusing forces the agent to acknowledge it is in the wrong place.

`init` from a worktree root **is** allowed. The worktree IS the resolved repo root from the worktree's perspective (its `.git` file anchors there). If you deliberately want a per-worktree workspace, that is now your explicit choice. Otherwise, set `IPMAN_HOME` to the parent's `.ipman/` before invoking ipman in the worktree.

---

## Migration

Nothing to do for clients that were already well-positioned. No protocol changes, no DB changes.

For agents/scripts that **were** relying on the legacy `./.ipman` resolution from a subdir:

- **Subdir reads**: now resolve to the repo-root `.ipman/`. If you were operating against a stray subdir-local `.ipman/`, you will see the parent workspace's data instead. If that breaks you, set `IPMAN_HOME=$(pwd)/.ipman` explicitly.
- **Subdir `init`**: now refuses. The error message tells you the relative path to the repo root. Either `cd` there or set `IPMAN_HOME` explicitly.
- **Outside-any-repo invocation**: unchanged. ipman still happily uses `./.ipman` when `cwd` is not under a `.git` ancestor.
