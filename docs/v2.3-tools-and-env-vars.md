# ipman v2.3 — project entity + requirements registry

> **v2.3.1 patch:** the `instruction` entity now accepts `entity_type='project'`
> (with `entity_id=1`), and `workspace.context_get` exposes those rows under
> `context.project.instructions`. See [v2.3.1 — project-scoped instructions](#v231--project-scoped-instructions)
> at the end of this document.

ipman v2.3 is **purely additive over v2.2**. The JSON protocol stays at `protocol_version: 2`; no operations were renamed or removed; every v2.0/v2.1/v2.2 client keeps working unchanged. What v2.3 adds is a first-class **project** entity (workspace-level metadata) and a **registry of project requirements**: which tools the project needs to run, and which environment variables it expects.

If you only consume ipman through the JSON wire and don't care about declaring requirements, **nothing in this release changes for you**. Skip to [Migration patterns](#migration-patterns) for the contract guarantees.

---

## What's new at a glance

| Group | Change | Replaces |
|---|---|---|
| Schema | New tables `project` (single-row), `tools`, and `env_vars` — all workspace-level | Documenting requirements in free-form comments or external README |
| Operations | `project.get`, `project.update`, `project.history`; full CRUD for `tool.*` and `env_var.*` | None — first-class API where there was nothing before |
| Context | `workspace.context_get` returns a `project` block (`name`, `description`, `tools[]`, `env_vars[]`) — sensitive examples masked unless `reveal:true` | Manually calling separate ops after each session start |
| Events | `project_updated`; `tool_added/updated/invalidated`; `env_var_added/updated/invalidated`; `entity_type='project'` allowed | — |
| Schema version | DB migrates 3 → 4 on first launch | — |

The three new ops on `project`, the four on `tool`, and the four on `env_var` total **11 new operations**. Surface grows from 65 to **76 ops across 12 entities** (added: `project`, `tool`, `env_var`).

---

## Why this exists

Before v2.3, "what is this project, and what does it need to run" lived in:

- A `README.md` section that drifts.
- A `.env.example` file that nobody updates.
- Tribal knowledge that walks out the door when the original author leaves.

Tools like [mise](https://mise.jdx.dev/) and [direnv](https://direnv.net/) solve part of the problem (pinning versions, loading env vars), but they don't capture **why** a tool is required, **who** added it, when it became obsolete, or what the project as a whole *is for*. ipman v2.3 plugs that gap with a queryable, auditable registry that agents and humans share.

It is **deliberately not a secret store**. The `env_vars` table has no `value` column — only the variable's name, purpose, and an optional non-secret example. Actual values still belong in `.env`, your CI's secret manager, or HashiCorp Vault.

## Entity: `project`

Single-row table. The row is initialized by migration 0004 with `name='unnamed'` and no description. Agents update it via `project.update` after init.

```text
id (always 1), name, description, created_at, updated_at
```

### Operations

```json
{"op":"project.get","params":{}}
// → {"project": {"id":1, "name":"ipman", "description":"...", "created_at":"...", "updated_at":"..."}}

{"op":"project.update","params":{
  "name":"ipman",
  "description":"Implementation Plan Manager — auditable plans for agents."}}

// project.history: project + tool + env_var changes plus major plan
// lifecycle events (created, closed, archived, reopened, activated,
// deactivated). Phase/task/comment events are excluded — those belong
// in plan.history.
{"op":"project.history","params":{"limit":50}}
```

### Why not a flat field on `workspace_context`?

`workspace_context` is for runtime cursor state (active plan, current phase/task). `project` is for stable, human-authored metadata. Mixing the two would couple a single-row state object to write-frequent navigation, and would make audit events (`project_updated`) fight with the heavier `plan_activated`/`phase_current_changed` traffic on the same row.

## Entity: `tool`

Project-scoped (no `plan_id`). One active row per tool name, enforced via partial unique index.

```text
id, name, version_constraint, purpose, install_hint, required,
author, created_at, updated_at, invalidated_at, invalidated_by
```

- `name` — required, unique among active rows.
- `version_constraint` — optional, opaque text. ipman does **not** parse semver. Use whatever shape your version manager understands: `">=20"`, `"1.21.x"`, `"22.11.0"`, `"latest"`.
- `purpose` — optional one-liner. Helps reviewers decide whether to keep the tool.
- `install_hint` — optional one-liner like `"mise use node@20"` or `"brew install jq"`. Useful for fresh-clone bootstrap.
- `required` — boolean, defaults to `true`. Set `false` for "nice to have" tooling.

### CRUD

```json
{"op":"tool.add","params":{
  "name":"node","version_constraint":">=20",
  "purpose":"runtime","install_hint":"mise use node@20"}}

{"op":"tool.add","params":{
  "name":"jq","required":false,
  "install_hint":"brew install jq"}}

{"op":"tool.list","params":{}}
{"op":"tool.update","params":{"id":3,"version_constraint":">=22"}}
{"op":"tool.invalidate","params":{"id":3}}
```

### Conflict semantics

Adding a tool with the same `name` as an existing **active** row returns `error.code = "conflict"`. To replace, invalidate the old row and add a new one — the audit trail records both transitions.

## Entity: `env_var`

Project-scoped (no `plan_id`). One active row per name, enforced via partial unique index.

```text
id, name, purpose, example, required, sensitive,
author, created_at, updated_at, invalidated_at, invalidated_by
```

- `name` — required, must match `^[A-Z_][A-Z0-9_]*$`. Lower-case names, hyphens, dots, and leading digits are rejected at the wire layer with `validation_failed`.
- `purpose` — **required** (unlike `tool.purpose`). For env vars the *why* is the most useful field a reviewer can read.
- `example` — optional sample value (e.g. `"postgres://localhost:5432/dev"`). For sensitive vars, write a non-secret placeholder, never a real key.
- `required` — boolean, defaults to `true`.
- `sensitive` — boolean, defaults to `false`. When `true`, `env_var.list` and `workspace.context_get` mask the `example` field unless the caller passes `reveal: true`.

### CRUD

```json
{"op":"env_var.add","params":{
  "name":"DATABASE_URL",
  "purpose":"primary postgres connection",
  "example":"postgres://localhost:5432/dev"}}

{"op":"env_var.add","params":{
  "name":"STRIPE_SECRET",
  "purpose":"payments webhook signature key",
  "example":"sk_live_REPLACE_ME","sensitive":true}}

{"op":"env_var.list","params":{}}
{"op":"env_var.list","params":{"reveal":true}}
{"op":"env_var.update","params":{"id":3,"sensitive":true}}
{"op":"env_var.invalidate","params":{"id":3}}
```

### Why no `value` column

ipman is committed to one repository per plan and frequently shared. Storing real secret values — even encrypted — would create a target for exfiltration and an unclear lifecycle (rotation? expiry?). The 12-factor pattern is correct: keep names and purpose in the registry, keep values in a real secret manager. The `sensitive` flag exists to let `ipman` be honest about which examples are placeholders for things you must never paste into chat or a PR description.

## Integration with `workspace.context_get`

Agents that bootstrap with `workspace.context_get` now receive a `project` block on the context object:

```json
{
  "context": {
    "active_plan_id": 1,
    "active_plan": {...},
    "current_phase": {...},
    "current_task": {...},
    "project": {
      "id": 1,
      "name": "ipman",
      "description": "Implementation Plan Manager — auditable plans for agents.",
      "created_at": "2026-05-03T...",
      "updated_at": "2026-05-03T...",
      "tools": [
        {"id":1,"name":"node","version_constraint":">=20","required":true, ...}
      ],
      "env_vars": [
        {"id":1,"name":"DATABASE_URL","sensitive":false,"example":"postgres://localhost:5432/dev","required":true, ...},
        {"id":2,"name":"STRIPE_SECRET","sensitive":true,"example":"[sensitive]","required":true, ...}
      ]
    }
  }
}
```

- The `project` block is **always present** (the project row exists from the moment migration 0004 runs).
- Only **active** tool/env_var rows are included (use `tool.list` / `env_var.list` with `include_invalidated: true` for history).
- Sensitive examples are **masked by default**. Pass `{"reveal": true}` to `workspace.context_get` to see the literal example.

## Events

Seven new event types join the allowlist, and `entity_type` now accepts `'project'`:

```
project_updated
tool_added           tool_updated           tool_invalidated
env_var_added        env_var_updated        env_var_invalidated
```

All seven attach to `entity_type='project', entity_id=1`, so they appear in `project.history` and `event.list --entity_type project` automatically.

`project.history` is a convenience alias that returns project-scoped events plus the major plan lifecycle events (`plan_created`, `plan_closed`, `plan_archived`, `plan_reopened`, `plan_activated`, `plan_deactivated`). Phase, task, and comment events are excluded — those belong in `plan.history`.

## Migration patterns

### Upgrading from v2.2

1. Build the v2.3 binary as usual (`make build`).
2. On the first invocation against an existing DB, migration `0004_tools_and_env_vars.sql` applies in a single transaction. The `events` table is rebuilt with the extended `entity_type` and `event_type` allowlists; row data is preserved. The `project` row is seeded with `name='unnamed'`.
3. No client-side changes are required. Existing v2.0/v2.1/v2.2 calls keep working byte-for-byte.

The migration is **forward-only** in the standard ipman model — once 0004 is recorded in `schema_metadata`, downgrading to a v2.2 binary will fail on startup with `DB schema newer than binary` (the existing safety check, unchanged from v2.0).

### Adopting the registry incrementally

You don't have to backfill everything on day one. A reasonable order:

1. **First session after upgrade** — set the project name and description (`project.update`).
2. **Then** — add the 2-3 tools the project absolutely cannot run without (`tool.add node`, `tool.add make`, etc.).
3. **Next time you touch onboarding** — add env vars as you encounter them in code.
4. **Optional cleanup** — invalidate entries that are no longer required as the project evolves.

You can run `workspace.context_get` after each addition to confirm the new entries appear under `context.project`.

## What's deliberately absent

- **No version checking.** ipman doesn't run `node --version` to verify the constraint. That's `mise`/`asdf`/`devbox`'s job; ipman is a registry, not a doctor.
- **No env var values.** See [Why no `value` column](#why-no-value-column).
- **No per-environment overrides** (dev/staging/prod). Document differences in `purpose` ("set in CI" vs "set locally"). If you need real per-env config, that belongs in your CI provider or vault.
- **No CLI flag wrappers** (e.g. `ipman --add-tool`). The wire surface is fully accessible through the standard JSON-on-stdin contract; CLI ergonomics may follow in a later patch release if there's demand.
- **No tool dependency graph.** Plain flat lists. If you have ordering constraints, document them in `purpose` text.
- **No multi-project per IPMAN_HOME.** The project table is single-row by construction (`CHECK id = 1`). One IPMAN_HOME = one project.

## v2.3.1 — project-scoped instructions

`instruction.add`, `instruction.list`, `instruction.update`, and
`instruction.invalidate` now accept `entity_type='project'` (with
`entity_id=1`) in addition to `plan`/`phase`/`task`. Project-scoped
instructions describe **repository-wide standing guidance** that should
survive plan lifecycle and reach the agent at every session start —
typical examples:

```json
{"op":"instruction.add","params":{
  "entity_type":"project","entity_id":1,
  "instruction_type":"constraint",
  "body":"Apache-2.0 + SPDX-License-Identifier in all source headers."}}

{"op":"instruction.add","params":{
  "entity_type":"project","entity_id":1,
  "body":"Run make test before merging any change."}}
```

### Surfacing in `workspace.context_get`

`context.project` gains an `instructions[]` array alongside `tools` and
`env_vars`. The bootstrap response now looks like:

```json
{
  "context": {
    "project": {
      "id": 1, "name": "ipman", "description": "...",
      "tools":        [ ... ],
      "env_vars":     [ ... ],
      "instructions": [
        {"id":2,"entity_type":"project","entity_id":1,
         "instruction_type":"guidance",
         "body":"Run make test before merging any change.","author":"hleal", ...}
      ]
    }
  }
}
```

Plan/phase/task-scoped instructions are **not** mixed into this array —
they remain reachable via `instruction.list` (and `ipman --next`).
Mixing them would muddle the "this is workspace-stable" semantics of the
project block.

### Validation

- `entity_type='project'` requires `entity_id=1`. Other values are
  rejected at the op layer with `validation_failed: "entity_id must be 1
  when entity_type is 'project'"`.
- The events allowlist (extended in 0004) already accepts
  `entity_type='project'`, so `instruction_added`/`updated`/`invalidated`
  events emitted at project scope land without further schema changes.
- `project.history` automatically captures these events because its
  filter already includes `entity_type='project'`.

### Migration

Migration `0005_project_scoped_instructions.sql` rebuilds the
`instructions` table to extend its `entity_type` CHECK to accept
`'project'`. Row data is preserved. This is the only DB change in
v2.3.1.

### Test coverage

`tests/integration/210_project_instructions.sh` covers add at project
scope, the `entity_id != 1` rejection, list/update/invalidate, the
`context.project.instructions[]` surface, and the audit events that flow
into `project.history`.
